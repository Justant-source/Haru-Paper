## 1. 제품 형태

```
[USB-C PD 어댑터] ──C to C──→ [하루종이] ──C to C──→ [M832]
                                  ↑
                          Wi-Fi로 서버 폴링
```

- 가로로 긴 인라인 블록. 양 끝에 USB-C 암 포트
- 전원 어댑터와 프린터 사이의 "선 중간 장치"로 보이게 한다

### **(v1.1) 크기 목표 수정 — 개발 보드와 배포 보드를 분리한다**

v1.0의 "PoC 목표 75 × 30 × 16mm (기성 보드 조합)"은 **ESP32-S3-DevKitC-1로는 물리적으로 불가능하다.** DevKitC-1 보드 단독이 약 69 × 26mm이고 핀헤더 포함 높이가 12mm를 넘는다. 여기에 양쪽 USB-C 브레이크아웃(각 약 20mm)과 벅 모듈이 더해지면 내부 길이만 110mm 안팎이 된다.

| 용도 | 보드 | 크기 목표 |
|---|---|---|
| **개발 (P0~P1)** | ESP32-S3-DevKitC-1 N16R8 (2포트, 로그·업로드 동시 가능) | 케이스 없음. 브레드보드 |
| **조립·배포 (P3~P5)** | 소형 ESP32-S3 보드 (S3-Zero / SuperMini 계열, **GPIO19·20 또는 자체 USB-C가 네이티브 USB에 연결된 것**) | **약 80 × 32 × 18mm** |
| 양산 (3단계) | 전용 PCB (WROOM-1 모듈 직접 실장) | 55 × 24 × 12mm |

- 소형 보드는 USB 포트가 하나뿐이라 개발에 부적합하다는 v1.0의 지적은 맞다. 하지만 **배포 기기는 조립 시 1회 플래시 후 OTA로만 업데이트**하므로 포트 하나로 충분하다. 개발 중 확정된 펌웨어를 그대로 굽는다
- 소형 보드에서 네이티브 USB 핀은 보드 자체의 USB-C 커넥터에 연결되어 있고 헤더에 안 나오는 경우가 많다. **구매 전 회로도에서 GPIO19/20 헤더 노출 여부를 확인**한다 (3.5의 실험 결과에 따라 헤더가 필요 없어질 수도 있다)

### 왜 ESP32-S3인가

| 후보 | USB 호스트 | 판정 |
|---|---|---|
| ESP32-S3 | ✅ USB OTG (Full Speed) | **채택** |
| ESP32-S2 | ✅ USB OTG | 가능하나 BLE 없음 |
| ESP32-C3 / C6 | ❌ USB Serial/JTAG 전용 | **불가** |
| ESP32 (오리지널) | ❌ 없음 | **불가** |

**S3를 고르는 부가 이유**: BLE가 있어 절전 설정 명령이 BLE 전용으로 밝혀져도 대응 가능하다. S2에는 이 퇴로가 없다.

**(v1.1) 프레임워크: ESP-IDF v5.x LTS 고정. Arduino-ESP32 아님.** USB 호스트(`usb_host`), OTA 롤백, Wi-Fi 프로비저닝이 전부 IDF 네이티브이고, Arduino 코어에는 USB 호스트 API가 없어 결국 IDF를 직접 호출하게 된다. `usb_host` API는 IDF 4.4 → 5.x 사이에 바뀌었으므로 버전을 `idf.py`와 문서에 명시한다.

## 3. 전원 설계

### 3.1 블록도 — **(v1.1) GPIO 매핑 정정**

```
[USB-C 암 · 입력]  (PD 트리거 보드의 자체 커넥터를 그대로 사용)
   CC1/CC2 → PD 트리거 → 9V 협상
   VBUS(9V) ──→ 벅 컨버터(고정 5V) ──→ 5V
                                        ├─→ ESP32-S3 (5V 핀)
                                        └─→ 폴리퓨즈 3A ──→ [USB-C 암 · 출력] VBUS

[USB-C 암 · 출력]
   VBUS ← 5V 고정 (PD/QC 신호 없음)
   CC1, CC2 ← 각각 10kΩ 풀업(Rp) → 5V/3A 광고
   D+ ←→ ESP32-S3 GPIO20 (USB_D+)     ← v1.0은 GPIO19/20 순서가 반대였다
   D− ←→ ESP32-S3 GPIO19 (USB_D−)
   D+/D− ← USBLC6-2 TVS
   GND 공통
```

- **(v1.1) 정정**: ESP32-S3에서 **GPIO19 = USB_D−, GPIO20 = USB_D+** 이다. v1.0의 "D+/D− ←→ GPIO19/GPIO20"은 순서가 반대다. 반대로 물리면 열거가 안 되고, 로직 애널라이저로 봐도 원인이 안 보인다
- 10kΩ Rp → 5V는 3A 광고가 맞다 (56k=기본, 22k=1.5A, 10k=3A)
- 입력 측 USB-C 커넥터는 PD 트리거 보드에 이미 있으므로 브레이크아웃은 출력 측에만 쓴다

### 3.2 핵심 제약

| 항목 | 값 | 근거 |
|---|---|---|
| 다운스트림 전압 | **5V 고정** | M832는 5V 어댑터만 지원, 고속충전 미지원 |
| 다운스트림에 PD 소스 | **넣지 않는다** | 위와 동일 |
| 업스트림 | **PD 9V** 수령 | 5V 3A는 케이블 전압강하로 불안정. **(v1.1) 12V는 PD 선택 사항이라 쓰지 않는다** |
| 번들 어댑터 | 30W 이상 PD, 9V PDO 확인 | |
| **(v1.1) 비PD 어댑터 삽입 시** | 트리거가 5V 폴백 → 벅이 드롭아웃 → 출력 4.5~4.8V | 프린터 충전이 약해질 수 있다. 사용자 안내 "동봉 어댑터만 사용" + 케이스 각인 |

### 3.3 전력 예산 — **(v1.1) 발열 재계산**

v1.0의 "13W를 이 부피에서 처리"는 **동글이 13W를 소산한다는 오해**다. 10W는 동글을 *통과해* 프린터로 가고, 동글 안에서 열로 바뀌는 것은 변환 손실과 ESP32 소비뿐이다.

| 항목 | 최악 (배터리 급속 충전 중) | 정상 상태 (배터리 만충, 기상 대기) |
|---|---|---|
| M832 인입 | 10W (통과) | 0.5~1.5W (통과, 추정) |
| 벅 손실 (효율 ~90%) | ~1.1W | ~0.2W |
| ESP32-S3 (Wi-Fi 활성, USB 호스트) | 0.6~1.5W | 0.6~1.0W |
| **동글 자체 발열** | **약 2~2.5W** | **약 1W** |

- M832 배터리는 첫 만충 후 인쇄 1장당 수십 mAh만 보충하므로, **10W 충전은 첫날과 장기 방치 후에만 일어난다**
- 2.5W를 80×32×18mm 케이스에서 소산하면 표면이 미지근한 정도. **통풍 슬롯은 넣되 설계 제약이 아니다**
- **(v1.1) P1에서 USB 전력계로 M832 정상 상태 인입 전력을 실측**해 표의 추정치를 채운다. 이 값이 어댑터 사양과 "13W" 논의를 끝낸다

### 3.4 D+/D− 배선 주의

- M832는 USB Full Speed(12Mbps)로 추정 (`wMaxPacketSize 64` 확인 시 확정). **(v1.1) 참고로 S3의 루트 포트는 FS 전용이라 M832가 HS였더라도 FS로 동작한다** — v1.0의 "HS였다면 불가능"은 과장이다. 손배선의 신호 품질이 문제일 뿐
- D+/D− 쌍은 **5cm 이내, 나란히, 꼬아서**. 전원선과 나란히 길게 가지 않도록
- TVS는 커넥터에 최대한 가깝게

### 3.5 **(v1.1 신설) 프린터 연결 전 검증 절차 — 필수**

M832는 12만 원짜리다. 전원 회로가 확인되기 전에는 물리지 않는다.

1. PD 트리거 단독: 어댑터 연결 → 멀티미터로 **9V** 확인
2. 벅 연결: 무부하 출력 **5.0~5.15V**
3. 부하 테스트: 5V 출력에 **2.5Ω/10W 저항(또는 전자 부하) → 2A 부하에서 4.9V 이상** 유지, 벅 모듈 온도 손으로 확인
4. ESP32 연결 후 Wi-Fi 활성 상태에서 다시 측정
5. 여기까지 통과해야 프린터를 물린다

**(v1.1) 선택 실험 — 소형 보드의 자체 USB-C를 다운스트림 포트로 쓰기**

소형 S3 보드는 대개 USB-C 커넥터의 VBUS가 보드 5V 네트에 직결되고 D+/D−가 GPIO19/20에 직결되어 있다. 그렇다면 **벅 5V → 보드 5V 핀 → 보드 USB-C 커넥터 → C to C 케이블 → M832**로 연결하면 브레이크아웃·D+/D− 손배선·Rp 저항이 전부 사라진다. 조립 난이도가 크게 내려간다.

- 조건: 보드 VBUS-5V 사이에 다이오드가 없어야 함 (회로도 확인). 커넥터의 CC에는 Rd(5.1k)가 있지만 M832는 CC를 보고 데이터를 막지 않을 가능성이 높다
- **리스크: 보드의 VBUS 트레이스가 2A를 감당하도록 설계되지 않았을 수 있다.** 2A 부하에서 트레이스 온도와 전압강하를 실측한 뒤 판단
- P1에서 30분짜리 실험. 성공하면 P3 조립 방식이 바뀐다

## 4. 펌웨어 설계

### 4.1 원칙 — 멍청한 파이프

```
서버:   콘텐츠 → 렌더 → 필터 → 완성된 프린터 바이트 스트림(.bin)
동글:   poll → .bin 전체 수신 → sha256 검증 → Bulk OUT 0x02 에 write → ack
```

- 펌웨어에 PNG 디코더, 비트 패킹, 프린터별 명령 로직이 없다
- 기기는 **날짜·폴링 주기·재시도 여부를 판단하지 않는다.** 전부 서버가 지시한다 (01 v1.2와 동일)
- 기기가 보유한 상태: Wi-Fi 자격증명 + 디바이스 토큰 (NVS) + CA 번들 (펌웨어 내장)

### 4.2 메모리 — **(v1.1) 스트리밍 write 폐기, 전체 버퍼링**

v1.0의 "통째로 버퍼링하지 않는다. 청크로 받아 곧바로 USB에 흘린다"를 **폐기**한다. 01 v1.2에서 정한 이유와 같다: 다운로드가 중간에 끊기면 **반쪽짜리 래스터가 프린터에 들어간 상태**가 되고, 그 잡은 `unknown`으로 남는다.

- 570KB는 PSRAM(8MB)에 `heap_caps_malloc(MALLOC_CAP_SPIRAM)`으로 통째로 받는다
- 수신하면서 mbedtls로 sha256 누적 계산 → `Content-Length`·해시가 서버가 준 값과 일치할 때만 write 시작
- **USB 전송 버퍼는 PSRAM이 아니다.** `usb_host_transfer_alloc()`이 주는 DMA 가능 내부 RAM 버퍼(예: 4~16KB)로 PSRAM에서 memcpy 해 가며 전송한다. 이것은 프로토콜 흐름제어가 아니라 호스트 라이브러리의 전송 단위일 뿐이다
- 내부 RAM 예산: Wi-Fi + TLS 핸드셰이크 + `usb_host` + (조건부) NimBLE. `CONFIG_MBEDTLS_EXTERNAL_MEM_ALLOC`로 TLS 버퍼를 PSRAM으로 보내 여유를 확보한다

### 4.3 모듈 구성

```
main/
├── provision.c        // SoftAP + 캡티브 포털로 Wi-Fi 설정. 버튼 5초로 재진입
├── net_time.c         // (v1.1) SNTP 동기화, 인증서 번들
├── api_client.c       // poll(POST, 상태 포함) / stream(전체 수신+검증) / ack
├── usb_printer.c      // USB 호스트: 열거, claim, bulk write, (v1.1) GET_PORT_STATUS
├── job_runner.c       // poll → stream → 검증 → 인쇄 → ack. 데드라인
├── ble_config.c       // (조건부) 절전 설정 명령 전송
├── ota.c              // A/B + 롤백. 첫 poll 성공 후 mark_valid
├── status_led.c       // (v1.1) RGB LED: 프로비저닝/연결/인쇄/오류
└── watchdog.c         // (v1.1) task WDT + "30분간 poll 실패 시 재부팅"
```

### 4.4 USB 호스트 구현

ESP-IDF `usb_host` 라이브러리. 표준 프린터 클래스라 전용 드라이버가 필요 없다.

```
1. usb_host_install()  — 데몬 태스크에서 usb_host_lib_handle_events() 루프
2. 클라이언트 등록 → 디바이스 연결 이벤트 → usb_host_device_open()
3. Configuration Descriptor 파싱 (라이브러리가 SET_CONFIGURATION 수행)
4. bInterfaceClass == 7 인터페이스 → usb_host_interface_claim()
5. Bulk OUT 엔드포인트(0x02) 확보
6. (v1.1) 01에서 GET_PORT_STATUS 가 반응했다면: 컨트롤 전송 1회로 용지 확인
   bmRequestType 0xA1, bRequest 0x01, wIndex=인터페이스, wLength=1
7. usb_host_transfer_submit() 으로 청크 전송 (완료 콜백 → 세마포어로 직렬화)
8. 전체 write 데드라인 60초 (01 v1.2와 동일)
```

**유리한 조건들**

| 항목 | 상태 | 의미 |
|---|---|---|
| 표준 프린터 클래스 7/1/2 | 확인됨 | 벤더 드라이버 불필요 |
| 상태 응답 읽기 | 불필요 (단, `GET_PORT_STATUS`는 표준 컨트롤 요청이라 별개) | 단방향 write |
| 페이싱/청킹 | 불필요 | 흐름제어 로직 없음 |
| Full Speed | 추정 | 손배선 허용 |
| Pi에서 검증된 .bin | 01 v1.2 산출물 | 프로토콜 변수가 없다 |

> **(v1.1) 난이도 재평가**: 디스크립터가 있고, Pi에서 같은 .bin이 찍히는 상태에서 `usb_host_lib` 예제를 출발점으로 삼으면 **소프트웨어는 1주 내외**다. 2~4주 중 나머지는 **손배선 하드웨어의 신호 품질과 전원 문제**에 들어간다. 즉 이 항목의 리스크는 코드가 아니라 납땜이다. 열거가 안 되면 순서: ① D+/D− 뒤바뀜 ② 브레이크아웃 A6/B6 미결선 ③ 5V 레일 흔들림 ④ 그 다음이 코드
> **(v1.1) BLE가 필요해지면 +1~2주.** Wi-Fi/BLE 라디오 공존 설정과 NimBLE 통합이 추가된다. 01의 결과가 나오면 여기를 갱신한다

### 4.5 전원 관리 — 없음

M832 앱에서 "자동 종료 설정 안함"이 가능하고 재부팅 후에도 유지됨이 확인되었다. **핑 로직, 로드 스위치, VBUS 제어, 배터리 잔량 제어를 전부 넣지 않는다.**

### 4.6 절전 설정 자동 복구 (조건부)

| 1단계 결과 | 2단계 구현 |
|---|---|
| USB Bulk OUT으로 전송 가능 | 매 인쇄 직전 1회 전송 |
| BLE 전용 | **(v1.1) 매 인쇄 직전 1회 BLE 전송** — v1.0의 "부팅 시 1회"는 삭제. 동글은 거의 재부팅되지 않으므로 공장 초기화가 부팅 뒤에 일어나면 복구가 안 된다 |
| 명령 특정 실패 | 출하 전 수동 설정 + 사용자 안내 |

### 4.7 **(v1.1 신설) 필드 배포 필수 항목** — Pi에는 없던 것들

Pi는 Tailscale 안에서 SSH가 됐다. 지인 집에 놓인 ESP32는 **원격 로그와 OTA 말고는 손댈 방법이 없다.** 아래는 P5 전에 전부 갖춰져야 한다.

| 항목 | 내용 |
|---|---|
| **서버 공인 HTTPS 전환** | 01은 Tailscale 내부망이었다. ESP32는 Tailscale에 못 붙는다. **P0에서** 공인 도메인 + 정식 CA 인증서(예: ALB/ACM)로 전환하고, 디바이스 토큰 인증 + 레이트리밋을 서버에 넣는다 |
| **인증서 신뢰** | `esp_crt_bundle` (Mozilla 루트 번들) 사용. **서버 리프 인증서를 핀하지 않는다** — 갱신 시 10대가 동시에 접속 불능이 된다 |
| **SNTP** | ESP32는 RTC가 없어 부팅 시 1970년이다. ESP-IDF 기본 설정은 인증서 유효기간 검사가 꺼져 있어 TLS 자체는 되지만, 검사를 켜면(권장) SNTP 동기화가 선행되어야 한다. 어느 쪽이든 로그 타임스탬프를 위해 부팅 직후 SNTP를 돌리고, 실패해도 poll은 계속한다 |
| **디바이스 토큰** | P3 조립 시 개발자가 서버에 기기를 사전 등록하고 토큰을 **NVS에 주입**한다. 기기가 스스로 register 하지 않는다 (10대 규모에서는 이게 가장 단순하다). 기기↔사용자 연결은 서버에서 수동 배정 |
| **원격 로그** | 메모리 링버퍼(최근 200줄) → poll 본문에 실어 전송 (01 v1.2와 동일). 이것이 유일한 디버그 채널이다 |
| **OTA A/B + 롤백** | `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`. 새 펌웨어는 **첫 poll 성공 후** `esp_ota_mark_app_valid_cancel_rollback()`. poll 응답에 `ota_url`이 있으면 다운로드·검증·리부트. **배포는 카나리 1대 → 24시간 → 나머지** |
| **자가 복구** | 30분간 poll 성공이 없으면 재부팅. Wi-Fi STA 끊김 이벤트에서 무한 재접속 |
| **프로비저닝** | SoftAP "HaruPaper-XXXX" + 캡티브 포털(esp_http_server + DNS 하이재킹)로 홈 Wi-Fi 입력. 앱 설치 불필요. BOOT 버튼 5초 → 자격증명 삭제 → 프로비저닝 재진입 |
| **상태 LED** | 프로비저닝 대기 / Wi-Fi 연결 중 / 정상 / 인쇄 중 / 오류. DevKitC-1의 WS2812 (GPIO38 또는 48, 보드 리비전 확인). 배포 보드도 RGB LED가 있는 것으로 |

### 4.8 방어 로직 — **(v1.1) 01 v1.2와 정합**

**삭제**: ~~job id 로컬 dedup~~, ~~당일 잡만 출력~~, ~~인쇄 실패 시 자동 재시도 1회~~, ~~heartbeat 엔드포인트~~

**유지·변경**:

- 중복 방지·만료·재시도는 **서버 잡 상태머신**(pending → delivered → done / failed / unknown / expired)이 담당. 기기는 `printed` / `download_failed` / `print_failed(reason)` ack만 보낸다
- poll(POST)에 기기 상태 포함: fw 버전, printer_connected, port_status, battery, wifi_reconnects, 링버퍼 로그. 응답의 `next_poll_seconds`만큼 대기
- 시각은 서버 기준. SNTP는 TLS·로그용
- **동글은 항상 깨어 있다.** USB 호스트는 슬립과 양립하지 않는다. 절전 설계 없음

## 5. 케이스 설계

### 5.1 순서

1. 부품 도착 → **캘리퍼스 실측** (배포 보드 외형, 나사 구멍, 커넥터 돌출)
2. 부품을 직육면체 더미로 모델링
3. 배치 검토 (케이블 꺾임 여유 최소 15mm)
4. 외피 셸 생성
5. **테스트 쿠폰** — 커넥터 포켓만 잘라 출력해 치수 확정
6. 전체 출력

### 5.2 수치 기준

| 항목 | 값 |
|---|---|
| 부품 주변 여유 | 0.3~0.5mm |
| 벽 두께 | 1.6~2.0mm |
| M3 나사 통과 구멍 | 3.3mm |
| 열 인서트 너트 구멍 | 4.1mm |
| 재질 | **PETG** |
| 레이어 / 인필 / 벽 | 0.2mm / 15% / 3줄 |

### 5.3 반드시 넣을 것

- USB-C 커넥터 주변 보강 — 스트레인 릴리프, 하단 지지 리브
- 통풍 슬롯 (3.3에 따라 필수 아님, 있으면 좋음)
- 상하 2분할 + M3 나사 4개
- **(v1.1) 포트 구분** — 양쪽이 똑같은 USB-C 암 포트라 사용자가 **어댑터와 프린터를 반대로 꽂을 수 있다.** 컴플라이언트 PD 어댑터면 아무 일도 안 일어나지만(양쪽 Rp → 미연결), 비표준 5V 어댑터를 출력 포트에 꽂으면 벅 출력에 역전압이 걸린다. **색상 링 + "IN / OUT" 각인 + 사용자 안내 그림**으로 막는다
- **(v1.1) 버튼 구멍** (프로비저닝 리셋) + **LED 라이트 파이프 구멍**
- **(v1.1) Wi-Fi 안테나 주변 금속 없음.** 보드 안테나가 케이블·벅 모듈 쪽을 향하지 않게 배치
- 각인: 제품명 / 5V 2A OUT / **"동봉 어댑터만 사용"** / 기기 ID 라벨 자리

### 5.4 모델링 도구와 **(v1.1) 3D 프린터 구매 시점**

- **build123d / CadQuery (Python)** — 치수를 변수로, git으로 버전 관리. 권장
- **3D 프린터는 P2 착수 시점에 산다.** 지금 사면 P0~P1 동안 놀고, 프린터 세팅·베드 레벨링·PETG 스트링 잡기가 그 자체로 1~2주짜리 부업이 된다. 첫 테스트 쿠폰 1~2개는 출력 대행(2~5일, 수천 원)으로 CAD 치수부터 확인하고, 반복 횟수가 많아진다고 판단될 때 산다

## 6. 일정 — **(v1.1) 병렬화와 버퍼**

| 단계 | 기간 | 내용 | 병렬 |
|---|---|---|---|
| **P0** 부품 대기 | 2~3주 | 알리 배송. 서버 공인 HTTPS 전환, USB 호스트 코드 선행 작성, 프로비저닝·OTA 뼈대 | **01의 30일 운영과 겹친다** |
| **P1** 브레드보드 1대 | 3~4주 | 3.5 전원 검증 → 열거 → **서버 .bin이 M832에서 인쇄됨** → 전력 실측 → (선택) 소형 보드 포트 실험 | 01 30일 후반과 겹침 |
| **P2** 케이스 설계 | 2~3주 | 실측 → 쿠폰(대행) → 3D 프린터 구매 → 전체 출력 | **P1 후반부터 착수** |
| **P3** 2~3대 조립 | 1~2주 | 배포 보드로 조립. 토큰 NVS 주입. 1대당 1~2시간 | |
| **P4** 자가 운영 | 4주 | 본인 집. **OTA 1회 실전 수행 포함** | |
| **P5** 10대 확장 | 2~3주 | 지인 베타. 사용자 안내서 1장 | |

**순차 합계 약 4.5개월 → 병렬화로 3.5~4개월. 본업 병행이므로 여기에 30% 버퍼를 더해 4.5~5.5개월을 실제 기대치로 둔다.** (BLE가 필요해지면 +1~2주)

**시간을 먹는 곳은 코드가 아니다.** 손배선 디버깅(P1), 케이스 반복(P2), 10대 수작업 조립(P3·P5)이 실제 병목이다. 코드는 01에서 이미 검증된 파이프를 옮기는 일이다.

### 마일스톤 판정

- P1 완료 = **S3 하드웨어 불확실성**이 사라지는 지점. (프로토콜 불확실성은 01에서 이미 사라졌다)
- P4 완료 = 300대 양산 판단 가능 지점

- [ ] **(v1.1) 전용 용지 재구매 발생** — 면도날 모델의 유일한 직접 증거. 최소 5명 이상 1회 재구매
- [ ] 자동 출력 성공률 95% 이상 (제품 영역 기준)
- [ ] 출력물 보존성 문제 해결 또는 제품 메시지 확정
