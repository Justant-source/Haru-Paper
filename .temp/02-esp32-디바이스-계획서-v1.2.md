## 1. 제품 형태 — (v1.2) 두 갈래, 기본은 독립형

### 1.1 (A) 독립형 BT 박스 — **[기본값]**

```
[아무 5V USB 어댑터] ──USB──→ [하루종이 박스: ESP32 + LED + 버튼]  ···BT(SPP)···  [M832]
                                                                              ↑
                                                              [M832 전용 5V 2A 어댑터] (기존 그대로)
```

- Pi PoC와 **같은 토폴로지**(전원 2개, 데이터는 무선). 01 v1.3에서 실물로 검증 중인 구성을 그대로 소형화한다.
- 우리 회로가 프린터에 전기를 공급하지 않는다 → **프린터를 태울 수 있는 경로가 없다.** 전원 회로·검증 절차·오삽입 리스크가 통째로 사라진다.
- 부품: 보드 1 + 케이스 + (보드 내장) LED·버튼. 그게 전부다.
- 단점: 벽 플러그 2개. "하나의 제품"으로 보이게 하려면 케이스 디자인과 안내로 푼다(프린터 옆에 두는 작은 박스).

### 1.2 (B) 인라인 전원 통과형 + BT — **보류**

v1.1의 인라인 동글 형태를 유지하되 데이터는 BT로 보내는 안. "플러그 1개"만 남기고 v1.1의 전원 회로(PD 9V 트리거·고정 5V 벅·폴리퓨즈·포트 오삽입 대책)가 전부 그대로 필요하다. **데이터 이득은 0이고 프린터 과전압 리스크만 남는다.** P4 베타에서 "플러그 2개가 불편하다"는 피드백이 실제로 나올 때만 재검토한다. v1.1 §3의 수치는 §3.2 부록에 보존한다.

### 1.3 (v1.2) 칩 선택 — transport가 정한다

| transport | 상태 | 가능한 칩 | 판정 |
|---|---|---|---|
| **BT Classic SPP (RFCOMM ch1)** | 전송 [확인됨·실물], 출력물 [미검증] | **원본 ESP32**(WROOM-32/WROVER-E). S2·S3·C3·C6·H2에는 BT Classic 없음 | **채택 [기본값]** — PSRAM 있는 **WROVER** 계열 |
| BLE GATT (M04 계열 `ff00`/`ff02`) | M832에서 **[추정]**, 미실험 | ESP32·S3·C3·C6 전부 가능 | 0원 실험(§2.1 G1)으로 되면 C3/C6(더 싸고 작음)도 후보. 안 되면 표에서 제거 |
| USB 호스트 | 바이트 [확인됨·실물], 단 운영 토폴로지에서 제외 | ESP32-S3·S2·P4 | **폴백 전용.** BT가 끝내 안 될 때만. 이 경우 v1.1 전체가 되살아난다 |

**왜 이제 S3가 아닌가**: v1.1은 "USB 호스트가 있고 BLE가 퇴로"라서 S3를 골랐다. 01 v1.3에서 USB 호스트가 필요 없어지고 **BT Classic이 필수**가 되면서, S3는 오히려 유일하게 못 하는 칩이 됐다.

**원본 ESP32 채택 시 알아둘 것** [추정, P1에서 실측]:
- BT Classic 스택은 **Bluedroid**(NimBLE은 BLE 전용). Wi-Fi + BT Classic 동시 사용은 소프트웨어 코엑시스턴스로 지원되나 동시 트래픽 시 처리량이 준다 → **PNG를 Wi-Fi로 다 받아 검증한 뒤, Wi-Fi 유휴 상태에서 SPP로 보낸다**(순차 사용).
- Bluedroid(Classic+BLE) + Wi-Fi + TLS를 한 번에 올리면 내부 RAM(520KB)이 빡빡하다 → **PSRAM 8MB 필수**(`CONFIG_SPIRAM`, `CONFIG_BT_ALLOCATION_FROM_SPIRAM_FIRST`, `CONFIG_MBEDTLS_EXTERNAL_MEM_ALLOC`).
- 개발 보드: **ESP32-DevKitC-VE**(ESP32-WROVER-E, PSRAM 8MB). 플래시는 판매 페이지의 모듈 코드(N4/N8/N16)로 확인하고 **8MB 이상**을 고른다(OTA A/B 2슬롯 + PNG 캐시 파티션, §4.5). 대개 micro-USB(일부 클론은 USB-C) — 케이블 종류 확인.
- 페어링: M832는 Just Works(PIN 없음, 01 v1.3 §1.2) → `ESP_BT_IO_CAP_NONE`. 본딩은 NVS에 남는다.

> **(v1.2) 검토 대상 선택지 — 사용자 결정**: 10대 베타의 목적이 "제품 가설 검증"이라면, ESP32 펌웨어(3~5주+)를 새로 쓰는 대신 **Orange Pi Zero 2W를 10대 그대로 쓰는 것**이 가장 싸고 빠를 수 있다(에이전트·BT가 이미 검증됨, 대당 약 3만 원, 케이스만 추가). ESP32는 300대 원가·크기 때문에 필요한 것이지 10대 때문이 아니다. 이 문서는 ESP32 경로를 계속 계획하되, **P0 게이트에서 이 선택지를 먼저 결정**하고 진행한다.

## 2. 구매 계획 — (v1.2 전면 개정) 게이트를 통과하기 전에는 아무것도 사지 않는다

### 2.0 원칙

1. **각 구매는 게이트에 묶인다.** 게이트 통과 전 발주 금지. "배송이 오래 걸리니 미리"는 이번 판에서 금지 — v1.1의 목록은 그 논리로 20여 종을 한꺼번에 사게 돼 있었고, 그중 대부분이 무용지물이 됐다.
2. **수량은 다음 게이트까지 필요한 만큼만.** 개발 보드 2개(1 사용 + 1 예비). "전부 2배수"는 폐기.
3. **국내에서 며칠이면 오는 것은 알리에서 사지 않는다.** ESP32 개발 보드는 국내 재고가 흔하다.
4. 이미 집에 있는 것(5V USB 어댑터, USB 케이블)을 먼저 센다.

### 2.4 프린터 2호기 — 유일하게 큰 구매 결정

- 지금 프린터는 **1호기 1대뿐**이고, 01 v1.3은 이 기기를 **30일 운영 전용**으로 못 박았다.
- ESP32 P1(§6)은 실제 프린터에 인쇄해야 끝난다. 30일 운영 **중에** 병행하려면 **2호기 1대**가 필요하다(BT는 여러 호스트와 본딩되지만 동시 연결은 1개이고, 무엇보다 1호기 용지·통계를 오염시키면 안 된다).
- **선택지**: ⓐ 2호기 1대를 **P1 착수 시점**에 산다(약 12만 원, 국내 유통) → 30일과 병행 / ⓑ 사지 않고 **30일이 끝난 뒤** 1호기로 P1을 한다 → 약 한 달 지연, 0원.
- v1.1의 "2~3대"는 ⓐ여도 **1대**로 줄인다. 10대분 프린터는 G3(P4 통과) 뒤에 산다.
- 어느 쪽이든 **직수입 금지, 국내 유통품**(수입자 책임).

## 4. 펌웨어 설계 — (v1.2) 실제 아키텍처와 정합

### 4.1 원칙 — "멍청한 파이프" 폐기, Pi 에이전트의 축소판

```
서버:   포맷·예약 저장 → 프로필 폭으로 그레이스케일 PNG 렌더 → /api/device/{poll,snapshot,renders,results}
기기:   poll(30s) → 스냅샷(예약·렌더 목록) 캐시 → PNG 다운로드·sha256 검증·캐시
        → 로컬 시계로 occurrence 계산 → 용지 정책 → [이미지 → 1-bpp → ESC/POS] → SPP 전송 → 결과 대기열 → 업로드
```

- **인터넷이 끊겨도 예약 시각에 인쇄한다**(PoC 완료 기준). 그래서 스케줄러·캐시가 기기에 있다. v1.1의 "기기는 판단하지 않는다"는 폐기.
- **m832를 아는 코드는 기기뿐이다**(`CLAUDE.md` 경계). 서버는 프로필(`model, dpi, paperWidthMm, printableWidthPx`)만 안다.
- 기기가 보유하는 상태: Wi-Fi 자격증명 + 기기 토큰 + BT 본딩(NVS), 스냅샷·PNG 캐시·결과 대기열(플래시 데이터 파티션), CA 번들(펌웨어).

### 4.2 이미지 파이프라인 — **[결정 필요, G1]**

Pi는 PNG를 받아 Pillow로 리사이즈·정렬보정·Floyd–Steinberg·패킹을 한다(`pi/printer/m832/image.py`). MCU에서 같은 일을 하는 두 가지 길:

| | (가) 서버가 1-bpp도 내준다 **[권장]** | (나) 기기가 PNG를 디코드·디더링한다 |
|---|---|---|
| 서버 변경 | 렌더에 `?format=1bpp`(또는 PBM) 추가 — **프로필 폭 기준 디더링은 프린터 무관한 범용 처리.** m832 명령 바이트·h-offset·163바이트 패딩은 서버에 넣지 않는다 → 경계 규칙 위반 아님 [해석, 사용자 확인 필요] | 없음 |
| 기기 처리 | 행마다 **3바이트(=24dot, h-offset 2.0mm) 0x00 prepend + 160바이트** → 163바이트 행. 헤더·꼬리 붙여 전송. **비트 시프트 없음**(24dot가 정확히 3바이트) | PNG 스트리밍 디코더(pngle 등) + 2행 오차확산 버퍼 + 패킹. 리사이즈는 서버가 프로필 폭으로 그리므로 생략 가능 |
| 메모리 | 1-bpp 페이지 = 163 × 높이(1725행이면 281KB) → PSRAM | PNG(압축, 수백 KB) + 디코더 상태 + 행 버퍼 → PSRAM |
| 검증 | 1-bpp 파일 sha256 → 전부 받은 뒤 전송 | PNG sha256 → 전부 받은 뒤 디코드하며 전송(디코드 오류가 중간에 나면 반쪽 래스터 — 검증된 PNG라 가능성 낮음) |
| 바이트 동일성 | 서버 디더링 결과가 Pi Pillow 결과와 **같지 않을 수 있다**(구현 차이) — 품질만 같으면 됨 | Pi와 구현이 달라 역시 다를 수 있음 |
| 공수 | 서버 1~2일 + 기기 1~2일 | 기기 1~2주 |

(가)를 택하면 `docs/architecture.md` 3.4/4.3의 렌더 API에 출력 형식이 추가된다 — **공통 문서라 사용자 승인 후 서버 세션이 반영**한다. (나)는 아키텍처 변경이 없지만 펌웨어가 무겁다. Pi도 나중에 (가)로 통일하면 이미지 처리 구현이 하나로 준다는 부수 효과가 있다.

### 4.3 BT SPP 클라이언트 (원본 ESP32, Bluedroid) [추정, P1 실측]

```
1. esp_bt_controller_init(BTDM) → esp_bluedroid_init/enable
2. GAP: IO capability NONE (Just Works). 본딩은 NVS 자동 저장
3. esp_spp_init → esp_spp_connect(sec=AUTHENTICATE, role MASTER, scn=1, bd_addr=C5:0D:F7:B7:B2:A1)
   (SDP 조회 생략 가능 — 채널 1은 [확인됨]. 조회를 쓰면 ESP_SPP_DISCOVERY_COMP_EVT의 scn 사용)
4. ESP_SPP_OPEN_EVT 후 esp_spp_write로 1~4KB 청크. ESP_SPP_CONG_EVT(혼잡)면 해제까지 대기.
   전체 write 데드라인 60초(01 v1.3 §4.2, Pi transport와 동일)
5. 전송 후 read: 프린터가 11바이트를 돌려준다(01 v1.3 §1.2, 의미 미해독). 로그에 남긴다 — H4 결과에 따라 용지 상태로 해석
6. 인쇄가 끝나면 연결을 닫는다(프린터가 폰 앱과 동시 연결을 못 받을 수 있음)
```

- **주소는 설정값**(`bt_address`, NVS). 페어링은 프로비저닝 화면에서 "프린터 연결" 버튼으로 1회.
- SPP 처리량 [추정]: 수십~100+ KB/s → 281KB 페이지 수 초. P1에서 실측해 §4.5 데드라인을 조정.
- **HCRP(L2CAP PSM 4107)는 쓰지 않는다** — 리눅스에서 EPERM으로 막혀 원인 미해결. SPP가 되므로 파지 않는다.
- **M832가 몇 시간 유휴 후에도 BT 연결을 받는가**는 [미검증]이다. V1은 전원 유지만 봤다. 01의 30일 운영이 이 답을 준다(제품 영역). ESP32는 그 결과를 물려받는다.

### 4.4 로컬 스케줄러·캐시·결과 대기열 (`docs/pi/agent.md`의 축소판)

| Pi 에이전트 | ESP32 대응 |
|---|---|
| SQLite `snapshot`/`renders`/`executed_occurrences`/`commands`/`results_queue`/`kv` | 플래시 데이터 파티션(LittleFS)에 JSON 파일 + NVS 키 몇 개. 테이블이 아니라 파일 |
| 30초 폴링, `snapshotChanged`면 스냅샷·렌더 재수신, `commands[]` 중복 제거 | 동일. `pollIntervalSec` 서버 지시 따름 |
| occurrence key `{scheduleId}@{date}T{HH:mm}`, 유예 30분·60초 재시도, `final` 기록 | 동일. 캐시할 렌더는 **"예약이 참조하는 포맷의 최신 1장"**으로 제한(플래시 절약) [기본값] |
| 시계 미동기면 인쇄 보류(`skipped_clock_unsynced`) | SNTP 동기 플래그. ESP32도 RTC 없음 → 정전+오프라인이면 같은 정책 |
| 결과 status 7종 (`policy.md` 5절) | 동일 문자열. 대기열 파일에 append, 업로드 성공 시 제거 |
| 보낸 바이트 30일 보관 | **하지 않는다**(플래시 수명·용량). 보낸 sha256만 결과 `detail`에 기록 [기본값] |
| 용지 정책 3종 | `unverified`·`manual_flag`는 그대로. `status_query`는 H4 통과 시 SPP read로 |

### 4.5 메모리·플래시 예산

- **PSRAM 8MB**: 1-bpp 페이지 또는 PNG + TLS 버퍼 + Bluedroid 동적 할당.
- **내부 RAM**: Wi-Fi + Bluedroid(Classic+BLE) + mbedTLS 핸드셰이크가 겹치는 순간이 최악. `CONFIG_BT_ALLOCATION_FROM_SPIRAM_FIRST`, `CONFIG_MBEDTLS_EXTERNAL_MEM_ALLOC`로 PSRAM에 밀어낸다. **P1에서 `heap_caps_get_free_size`를 로그에 찍어 확인.**
- **플래시 8MB 이상**: OTA A/B 앱 슬롯 2×(2~2.5MB) + 데이터 파티션(스냅샷 JSON, 렌더 캐시 2~3장 × ≤500KB, 결과 대기열) ≥ 2MB. 4MB 모듈은 A/B와 캐시를 같이 못 넣는다.

### 4.9 방어 로직 — (v1.2) `docs/pi/policy.md`와 정합

- **중복 방지는 기기 로컬**(occurrence key, command id, `final` 플래그). 전송 도중 죽으면 재시작 후 **자동 재인쇄하지 않고 `failed`** — "안 나옴 ≥ 두 장 나옴".
- 결과 업로드는 `resultId` 멱등. 명령 완료도 결과로 보고. 서버 명령은 10분 뒤 만료.
- 시각은 로컬(KST), 서버 `serverTime`과 크게 어긋나면 경고만.
- **기기는 항상 깨어 있다.** 절전 설계 없음(폴링·BT 연결 대기).

- 각인: 제품명, 기기 ID 라벨 자리. ~~"5V 2A OUT", "동봉 어댑터만 사용", IN/OUT 색상 링~~(출력 포트가 없다).
- 수치 기준(여유 0.3~0.5mm, 벽 1.6~2.0mm, M3 3.3mm, 인서트 4.1mm, PETG)은 v1.1 유지.
