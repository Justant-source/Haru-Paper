# Pi 에이전트 잔여 과제 3건 설계서 (v1.0)

> 대상 커밋: `107a06d` (clean). 이 문서는 **설계만** 한다 — 코드는 구현자가 쓴다.
> 세 과제(유예 내 재시도 없음 / "지금 인쇄" 실행기 없음 / `attempting` 정리 결과 미업로드)는
> 모두 `pi/agent/`의 **같은 상태 모델**을 건드리므로 하나의 설계로 묶는다.
> 규약 원본: `docs/architecture.md`(API·결과), `docs/pi/policy.md`(정책·유예), `docs/pi/agent.md`(에이전트 동작).

> 하드웨어는 건드리지 않았다 — 이 문서의 모든 "[확인됨]"은 **코드·문서 확인**이지 실물 인쇄 확인이 아니다.

## 0. 한 줄 요약

`executed_occurrences.final`의 의미를 **"이 occurrence는 끝났다"**로 좁히고, "이번 시도의 결과"는
`status` + `last_attempt_at`으로 따로 표현한다. **바이트가 프린터로 나갔을 가능성이 있는 시도만 무조건 종결**시키고,
그 전 단계에서 끝난 시도(용지 미확인·프린터 오프라인·렌더 없음)는 유예 안에서 60초 간격으로 재시도한다.
결과(`results_queue`)는 **`final=0 → final=1` 전이 때 정확히 한 번만** 만든다 — 이 한 가지 규칙이 과제 1·3과
"앱 이력에 회차가 빠지는 문제"를 동시에 푼다.

### 1.1 과제 1 — 유예 내 재시도가 없다

| 사실 | 근거 |
|---|---|

| 그래서 07:00에 건너뛰면 그날 그 예약은 끝 | 위 두 줄의 조합. 07:05에 용지를 넣어도 `final=1`이라 다시 후보가 되지 않는다 |
| 문서가 요구하는 동작 | `docs/pi/policy.md:45` "예약 시각 + 30분까지 **60초 간격으로 재시도**", `docs/pi/agent.md:126` "재시도: 마지막 시도 후 `HARU_RETRY_INTERVAL_SEC`(60초)가 지났을 때만" |

부수적으로 확인한 저장소 버그 2건(재시도 설계에 직접 영향):

1. **`first_attempt_at`이 갱신 때마다 덮어써진다.** `pi/agent/storage.py:229-231`이 인자가 없으면 `now`를 쓰고,
   `:249-256`의 `REPLACE INTO`가 행 전체를 갈아끼운다. 기존 행의 값을 읽지 않는다.
   실측(`pi/.venv`로 직접 실행):
   `save(..., first_attempt_at='2026-09-17T07:00:00')` → 1초 뒤 `save(..., final=True)` 하면
   `first_attempt_at`이 `13:28:56…`으로 바뀐다 [확인됨].
2. **`last_attempt_at` 인자는 무시된다.** `:255`의 튜플이 파라미터가 아니라 `now`를 넣는다.
   재시도 간격 판정의 기준값이 될 컬럼이므로 그대로 두면 안 된다.
3. 시각은 전부 **naive** `datetime.now()`(`storage.py:229`)다. 스케줄러·실행기는 KST aware
   (`scheduler.py:12`, `executor.py:21`)를 쓴다. 지금은 비교하는 코드가 없어 드러나지 않지만,
   재시도 간격은 "aware now − 저장된 문자열"을 빼야 하므로 이 불일치가 바로 `TypeError`가 된다.

### 1.3 과제 3 — `attempting` 정리 결과가 서버에 안 간다

- `storage.cleanup_stale_attempts()`(`storage.py:259-296`)는 `attempting`·`final=0`을 `failed`·`final=1`로 UPDATE만 한다.
  `results_queue`는 건드리지 않는다. 한계는 코드 주석(`:269-274`)과 `docs/pi/agent.md:152`에 이미 적혀 있다.
- 원인은 보고된 대로다: `executed_occurrences`에 `format_id`·`render_id`·`scheduled_at`·`detail`이 없다(DDL `storage.py:56-68`).
- **같은 뿌리의 미보고 결함 1건을 새로 찾았다**: 유예 만료 처리(`__main__.py:307-330`)도 `save_executed_occurrence`만 부르고
  `save_result`를 부르지 않는다. 즉 **`missed`는 지금 단 한 번도 서버에 올라간 적이 없다** — Pi가 꺼져 있던 회차는
  앱 이력에 아예 나타나지 않는다. 과제 3과 정확히 같은 증상이고 같은 수정으로 같이 풀린다 [확인됨·코드].
- 유예 만료 처리의 추가 결함 2건:
  - `existing_occs`를 **틱 시작 시점의 스냅샷**(`__main__.py:294-300`)으로 쓰므로, 같은 틱에서 3단계 실행 후 4단계가
    도는 사이의 변화를 못 본다. 지금은 "실행 가능 = 유예 안"이라 겹치지 않지만, 재시도를 넣으면 유예 경계 틱에서
    방금 기록한 결과를 덮어쓸 수 있다.
  - `status=existing.get("status", "missed")`(`:321`)는 직전 상태가 `attempting`이면 `attempting`을 그대로 최종 상태로
    남긴다 — 서버 ENUM에 없는 값이다.

## 2. 설계 결정과 근거 (질문 6개에 대한 답)

### Q1. 재시도 상태 모델 — `final`의 의미

**결정**

- `final = 1` ≡ **"이 occurrence는 끝났다. 다시는 시도하지 않는다."** (지금과 같은 뜻, 다만 이제는 아무 결과에나 붙지 않는다)
- **"이번 시도는 끝났다"는 `final`이 아니라 `status` + `last_attempt_at`으로 표현한다.** `final=0`인 행의 `status`는
  "마지막 시도의 사유"이고, 재시도 판정은 `now - last_attempt_at >= retry_interval_sec`로 한다.
- **재시도 가능 여부는 status 문자열에서 유추하지 않는다.** 실행기가 결과를 만드는 그 자리에서 정한다 —
  "프린터로 바이트가 나갔을 수 있는가"는 실행기만 아는 사실이고, 같은 `failed`라도 답이 다르기 때문이다.
  실행기는 지역 변수 `sent_possible`(아래 Q1 표)로 판단해 `final`을 정한다.

**`skipped_*`와 `failed`를 같게 보는가** → **아니다. 갈리는 기준은 status가 아니라 "전송 시작 여부"다.**
`skipped_*`는 정의상 전송 전이므로 항상 재시도 대상이고, `failed`는 전송 전(렌더 없음)이면 재시도, 전송 중이면 종결이다.

**대안과 기각 사유**

| 대안 | 기각 사유 |
|---|---|
| `final` 대신 `status in (...)` 화이트리스트로 재시도 판정 | 전송 중 실패와 전송 전 실패가 둘 다 `failed`라 구분 불가 → 중복 인쇄 위험. status는 서버 규약(ENUM 7종)에 묶여 있어 세분화도 못 한다 |
| 새 컬럼 `retryable` 추가 | `final`의 부정과 항상 같은 값이다. 두 개를 두면 어긋날 수 있다 |
| 전송 실패도 재시도(사용자가 "안 나왔다"고 느끼는 걸 줄이려고) | CLAUDE.md·`docs/pi/agent.md:150-151`의 "안 나옴 ≥ 두 장 나옴"을 정면으로 어긴다. 부분 인쇄 후 재전송 = 두 장 |
| `attempting` 하나로 "준비 중"과 "전송 중"을 겸용 | 기동 정리(`cleanup_stale_attempts`)가 `attempting`만 보고 종결시키므로, 준비 단계에서 죽은 것까지 종결된다. `checking`/`attempting`으로 나눈다(Q1 표 참조) |

### Q2. 유예 만료 처리는 어디에 있어야 하는가 / 지금 있는가

**지금 있다** — `__main__.py:307-330`(스케줄러 틱 4단계). 자리는 맞다. 다만 1.3에서 적은 대로
(a) 결과를 큐에 넣지 않고, (b) 틱 시작 시점의 스냅샷을 쓰며, (c) `attempting`을 그대로 최종 status로 남긴다.

**결정**: 자리는 그대로(스케줄러 틱, 실행 뒤 마지막 단계) 두고, 세 가지를 고친다.
1. 4단계 진입 전에 `executed_occurrences`를 **다시 읽는다**(3단계에서 방금 쓴 값을 본다).
2. 종결 시 반드시 `Executor.finalize_occurrence(...)`를 거쳐 **결과를 큐에 넣는다**.
3. 비종결 status(`checking`, `attempting`)는 `failed`로 매핑한다(서버 ENUM 보호).

`missed`의 정의(`docs/pi/policy.md:46`)에 맞춰, **시도 기록이 아예 없는 회차만 `missed`**, 시도했지만 조건 미충족이면
**마지막 사유**를 그대로 최종 status로 쓴다.

### Q3. 스키마 변경이 필요한가 — 필요하다 (5절에 상세)

`executed_occurrences`에 `format_id`·`render_id`·`scheduled_at`·`detail`을 추가하지 않으면 과제 3을 풀 수 없다.
현재 저장소에는 **마이그레이션 개념이 아예 없다** — `_init_schema()`(`storage.py:23-110`)의 `CREATE TABLE IF NOT EXISTS`가 전부라
기존 Pi의 `/var/lib/haru-paper/agent.db`는 새 컬럼 없이 그대로 열린다(오류도 안 난다 — 조용히 옛 스키마로 돈다).
→ `PRAGMA table_info` 기반의 **멱등 `ALTER TABLE ... ADD COLUMN`** 마이그레이션을 넣는다(5절).

### Q4. `paperConfirmed` 경로의 안전성

**신뢰 사슬** (코드로 추적한 실제 경로)

1. 앱: 체크박스 — `unverified`면 필수, 체크 전에는 버튼 비활성(`app/web/src/pages/PrintNowPage.tsx:124-143`, `:211`)
2. 서버: **검증하지 않고 그대로 저장**한다. `false`여도 거절하지 않는 것이 규약(`docs/architecture.md:291`, `PrintNowController.java:96`)
3. 서버 → Pi: poll 응답 `commands[]`(소유자 스코핑, `DeviceSyncService.java:118`)
4. Pi: 이 불리언 하나로 래스터를 보낸다 ← **절대 금지 1의 유일한 예외 경로**

**사슬이 끊길 수 있는 지점과 처리**

| # | 끊기는 지점 | 결론 |
|---|---|---|
| B1 | 앱 UI를 거치지 않고 `curl -d '{"paperConfirmed":true}'` | **Pi에서 막을 수 없다.** 자기 계정·자기 프린터이고 서버가 의도적으로 통과시키는 규약이다. 수용하고 문서에 명시 |
| B2 | **시간 경과**: 확인 후 Pi가 오프라인이었다가 9분 뒤 실행 / 용지가 그 사이 떨어짐 | **Pi가 자체 TTL을 건다.** `min(createdAt, received_at) + HARU_COMMAND_TTL_SEC(기본 600)`을 넘긴 명령은 래스터를 보내지 않는다. 서버 만료(10분)에 의존하지 않고 **Pi가 독립적으로** 판단한다 — "서버가 안 보냈겠지"는 fail-open이다 |
| B3 | 전송 중 죽은 명령이 재시작 후 다시 실행 | 명령도 occurrence와 같은 `attempting` → 기동 정리 → `failed` 종결(재실행 금지) |
| B4 | 한 번의 확인으로 여러 번 재시도 | **수용**한다. 재시도는 "아직 한 장도 안 나온" 상태에서만 일어나고(전송 시작 후엔 종결), TTL 10분 안이다. 용지를 소모하지 않은 확인은 여전히 유효하다고 본다 [기본값] |
| B5 | `paperConfirmed`가 `null`/문자열/누락 | **`is True`로 엄격 비교**한다(`cmd.get("paperConfirmed") is True`). `bool()`·`int()` 변환은 `"false"` 같은 값을 참으로 만든다. 1.2의 `TypeError`도 같이 사라진다 |
| B6 | 정책이 `status_query`인데 `paperConfirmed`로 우회 | **막는다.** `docs/pi/policy.md:30`이 "`paperConfirmed`는 이 정책에서 아직 참고되지 않는다"라고 못박았다. 구현에서 `status_query` 분기는 `paper_confirmed` 인자를 아예 보지 않는다 |
| B7 | 예약(무인) 실행이 `paperConfirmed` 경로를 타는 것 | **구조적으로 차단**: `_check_paper_policy(render, paper_confirmed=False)`의 기본값을 `False`로 두고, `execute_occurrence`는 이 인자를 **넘기지 않는다**. 테스트로 고정(6절 T12) |

### Q5. 명령 실행과 예약 실행의 관계 — 직렬화

**결정: 명령도 스케줄러 스레드에서 실행한다.** 폴링 스레드는 "받아서 저장"만 한다(지금과 같음).
프린터로 나가는 모든 경로가 **한 스레드**에 모이므로 구조적으로 직렬화된다.

- 지연: poll(최대 30초) + 다음 틱(최대 10초) = 최대 40초. `docs/pi/policy.md:78`의 "최대 30초"를 넘긴다.
  → `time.sleep(tick_interval)`을 `threading.Event.wait(tick_interval)`로 바꾸고, 폴링이 새 명령을 저장하면 `set()` 한다.
  이러면 명령은 사실상 poll 직후에 실행되고 평상시 틱 주기는 그대로다.
- **추가로 `Executor`에 `threading.Lock`을 둔다**(`print_image` 호출 + 상태 기록 구간). 지금은 불필요하지만,
  "프린터로 나가는 구간은 한 번에 하나"라는 불변식을 코드에 남기는 값이 있고 비용이 사실상 0이다.

| 대안 | 기각 사유 |
|---|---|
| 폴링 스레드에서 바로 실행(Lock만 사용) | BT 전송 데드라인이 60초다. 폴링 루프가 그만큼 멈추면 결과 업로드·`paperState` 갱신·다음 poll이 전부 밀린다 |
| 실행 전용 세 번째 스레드 + 큐 | 지금 필요 없는 복잡도. 스케줄러 틱이 이미 실행 전용 루프다 |

**SQLite 동시성**: 쓰기 주체가 두 스레드인 상태는 그대로다. `sqlite3.connect(..., timeout=5.0)`을 붙이는
작은 보강을 권한다(선택). WAL 전환은 SD카드 쓰기 패턴이 바뀌므로 **범위 밖**.

### Q6. 명령 만료 / `sha256` 검증 실패

| 상황 | 처리 |
|---|---|
| Pi가 늦게 실행(TTL 초과) | 래스터를 보내지 않고 `missed`(detail: `"명령 유예 초과(TTL 600초)"`)로 종결 + 결과 업로드. 서버의 `expired`와 별개로 **Pi가 스스로** 판단한다 |
| 결과를 올리면 서버가 `expired` → `done`으로 덮어쓴다 | **수용**한다(`ResultIngestService.java:58-66`). 명령 status는 서버 내부값이고, 앱 이력에 "왜 안 나왔는지"가 남는 쪽이 `missed`가 통째로 사라지는 것보다 낫다. 이 비대칭을 `docs/pi/agent.md`에 한 줄 적는다 |
| `sha256` 불일치 | **절대 인쇄하지 않는다.** 캐시를 버리고 다음 poll에서 다시 받는다. TTL까지 못 고치면 `failed`(detail: `"명령 렌더 sha256 불일치"`)로 종결 |
| 명령 `sha256`이 빈 문자열(서버가 렌더를 못 찾음, `DeviceSyncService.java:124-131`) | 검증 불가 = fail-closed. 다운로드하지 않고 TTL까지 대기 후 `failed`(detail: `"명령 렌더 sha256 없음"`) |
| 렌더가 아직 안 받아졌다 | 종결하지 않고 다음 틱 재시도(`docs/pi/agent.md:141`). TTL이 상한이다 |
| 명령 렌더를 못 받았을 때 스냅샷 렌더로 대체 | **금지.** 명령은 사용자가 지금 고른 내용이다. 다른 내용을 인쇄하는 것이 안 나오는 것보다 나쁘다 |

## 3. 상태 전이표

### 3.1 시도 단계 (실행기 내부, `executed_occurrences.status`)

| 내부 status | 뜻 | `final` | 바이트가 나갔을 수 있나 |
|---|---|---|---|
| `checking` | 렌더 선택·용지 판단·프린터 상태 조회 중 | 0 | **아니오** |
| `attempting` | `print_image()` 호출 직전~반환 전 | 0 | **예** |

`attempting`은 `print_image` **직전 한 줄**에서만 찍는다. 이 구분이 중복 인쇄 판정 전체의 근거다.

### 3.2 결과 status × 재시도 × 종결

`R` = 유예 안이면 재시도(`final=0`), `T` = 즉시 종결(`final=1`).

| 결과 status | 발생 지점 | 재시도 | `final` | 근거 |
|---|---|---|---|---|
| `printed` | 전송 성공 | ✗ | **T** | 성공. 다시 보내면 두 장 |
| `dry_run` | `unverified` 예약 | ✗ | **T** | 정책값은 서비스 재시작 전에는 안 바뀐다 → 30번 재시도해도 결과가 같다. `policy.md:45`의 재시도 사유("Pi 꺼짐·프린터 무응답·용지 없음 판정")에도 해당하지 않는다. 이력이 같은 회차로 30줄 늘어나는 것도 막는다 |
| `skipped_no_paper` | `manual_flag` 꺼짐, `status_query`, 명령 `paperConfirmed=false` | ✓ | **R** | 사용자가 롤을 갈고 앱에서 켜면 다음 poll에 `paperState`가 바뀐다 — **이 설계의 주 목적** |
| `skipped_printer_offline` | **전송 전** 상태 조회 실패 | ✓ | **R** | 07:00에 프린터가 꺼져 있고 07:05에 켜는 경우. 바이트는 안 나갔다 |
| `failed` (렌더 없음/미검증/파일 없음) | `_select_render`·`_load_render_bytes` | ✓ | **R** | 다음 poll(30초)에 렌더가 도착할 수 있다 |
| `failed` (**전송 중** 예외·타임아웃) | `print_image` 예외 | ✗ | **T** | 부분 인쇄 여부를 알 수 없다. `agent.md:150-151` |
| `failed` (전송 전 알 수 없는 예외) | `sent_possible=False`인 예외 | ✓ | **R** | 아무것도 안 나갔으므로 재시도 안전 |
| `failed` (전송 후 알 수 없는 예외) | `sent_possible=True`인 예외 | ✗ | **T** | 위와 같은 이유로 종결 |
| `failed` (재시작 후 `attempting` 정리) | 기동 정리 | ✗ | **T** | 기존 규칙 유지(`agent.md:151`) |
| `missed` | 유예 만료 + 시도 기록 없음 | ✗ | **T** | `policy.md:46` |
| (유예 만료 + 시도 기록 있음) | 마지막 사유를 그대로 최종 status로 | ✗ | **T** | `policy.md:46` |
| `skipped_clock_unsynced` | — | — | — | **미구현. 이 설계의 범위 밖**(9절) |

### 3.3 명령(commands) 상태 전이

로컬 `commands.status`: `pending` → `checking` → `attempting` → `done`.
`done`은 **"로컬에서 종결됨"**이라는 뜻이고, 인쇄 성공 여부는 업로드한 결과 payload의 `status`에 있다.

| 조건 | 다음 | 결과 payload status |
|---|---|---|
| 렌더 미수신/미검증, TTL 안 | `pending` 유지(재시도) | — |
| 용지 게이트 통과, 전송 성공 | `done` | `printed` |
| 용지 게이트 불통과 | `pending` 유지(재시도, `last_attempt_at` 갱신) | — |
| 용지 게이트 불통과 + TTL 만료 | `done` | `skipped_no_paper` |
| 프린터 오프라인(전송 전) | `pending` 유지(재시도) | — |
| 전송 중 예외 | `done` | `failed` |
| TTL 만료, 렌더 끝내 없음 | `done` | `failed`(detail: 사유) |
| TTL 만료, 그 밖 | `done` | `missed`(detail: `"명령 유예 초과"`) |
| 기동 시 `attempting`으로 남음 | `done` | `failed`(detail: `"전송 중 중단(재시작)"`) |

**결과는 `done` 전이 때 정확히 한 번만 큐에 넣는다** — occurrence와 같은 규칙.

## 5. SQLite 스키마 변경

**현황**: 마이그레이션 장치가 없다(`storage.py:23-110`은 `CREATE TABLE IF NOT EXISTS`뿐). 운영 Pi의
`/var/lib/haru-paper/agent.db`는 이미 데이터가 있고 서비스가 상시 구동 중이다.

### 5.1 추가 컬럼

| 테이블 | 컬럼 | 타입 | 용도 |
|---|---|---|---|
| `executed_occurrences` | `format_id` | TEXT | 결과 payload 재구성(과제 3) |
| | `render_id` | TEXT | 〃 |
| | `scheduled_at` | TEXT | 〃 (ISO-8601 +09:00) |
| | `detail` | TEXT | 〃 (실패 사유) |
| `commands` | `attempts` | INTEGER | 재시도 횟수 |
| | `last_attempt_at` | TEXT | 재시도 간격 판정 |
| | `detail` | TEXT | 결과 payload |

### 5.2 마이그레이션 방식

**결정: `PRAGMA table_info` 기반 멱등 `ALTER TABLE ... ADD COLUMN` + `PRAGMA user_version`.**

```python
SCHEMA_VERSION = 2   # 1 = 최초(2026-09-17 이전), 2 = 재시도·결과 재구성 컬럼 추가

def _migrate(self) -> None:
    """기존 DB(상시 구동 중인 Pi)를 파괴하지 않고 컬럼만 더한다.
    SQLite의 ADD COLUMN은 기본값 없이 붙이면 기존 행에 NULL이 들어가고 테이블 재작성이 없다(즉시 완료).
    table_info로 실제 컬럼을 보고 없는 것만 붙이므로, user_version이 어긋나 있어도(수동 조작·롤백 후 재배포)
    안전하게 한 번 더 돌 수 있다 — user_version은 기록용이고 판정 근거가 아니다."""
```

- `_init_schema()`(신규 DB) 뒤에 항상 `_migrate()`를 호출한다 → 새 DB는 no-op.
- 하나의 트랜잭션에서 모든 ADD COLUMN을 처리하고 마지막에 `PRAGMA user_version = 2`.
- **롤백 계획**: 새 컬럼은 옛 코드가 읽지 않으므로, 구현을 되돌려도 DB는 그대로 돈다(컬럼만 남는다). DROP 불필요.

### 5.3 옛 행(새 컬럼이 NULL) 처리

기동 정리·유예 만료가 옛 행을 종결시킬 때 `format_id`/`render_id`/`scheduled_at`이 NULL일 수 있다.

- `format_id`/`render_id`가 NULL → 빈 문자열로 올린다. 서버 `results.format_id`/`render_id`는
  `CHAR(36)` **NULL 허용**이고 NOT NULL이 아니다(`V1__init.sql:74-75`) [확인됨·코드].
- `scheduled_at`이 NULL → `occurrence_key`에서 복원한다(`scheduler.parse_occurrence_key` + KST).
  이게 key 형식의 존재 이유다. 복원도 실패하면 `null`로 올린다 — 서버 검증은 `scheduledAt` NULL을 허용한다
  (`DeviceSyncService.java:275`는 값이 있을 때만 형식을 본다) [확인됨·코드].
- `detail`이 NULL → `""`.

### 5.4 시각 표기

새로 쓰는 시각은 전부 **KST aware ISO-8601**(`+09:00`)로 저장한다. 읽을 때는 `clock.parse_local_iso`가
naive 문자열(기존 행)에 KST를 붙인다. `results` payload의 `scheduledAt`/`executedAt`도 오프셋이 있어야 한다
(`DeviceSyncService.java:270-283`의 `must be ISO-8601 with offset`).
