### 1.2 거부로 켰을 때 Pi에 실제로 무슨 일이 생기나 (정확히)

"Pi가 멈춘다"는 표현을 코드로 확인했다. **에이전트는 죽지 않는다.** 대신:

1. `pi/agent/sync.py:114-123` `download_render()`가 404에 `raise_for_status()` → 예외.
2. `pi/agent/__main__.py:243-244`가 그 예외를 렌더 단위로 잡고 ERROR 로그만 남긴다 → 폴링은 계속된다.
3. 그래서 그 렌더는 **로컬에 캐시되지 않는다.**
4. 예약 시각이 되면 `pi/agent/executor.py:48-53` `_select_render()`가 `None`을 돌려주고 결과가 `status="failed", detail="No render found"`로 서버에 올라간다.

→ **증상은 "조용한 매일 인쇄 실패"**다. 크래시가 아니라서 알아채기 어렵다. 이것이 A를 조심스럽게 다뤄야 하는 이유다.

### 1.4 **선택 전에 반드시 확인해야 했던 것 — "NULL이 다시 생기는 경로"**

`format.getOwnerUserId()`가 NULL일 수 있는 경우를 전부 훑었다.

| # | 경로 | 상태 | 근거 |
|---|---|---|---|
| 1 | M6 이전에 만들어진 레거시 포맷(`V2`가 컬럼을 NULL로 추가) | **살아 있음 — claim-legacy로만 없어진다** | `V2__users_and_ownership.sql` "ALTER TABLE `formats` ADD COLUMN `owner_user_id` CHAR(36) NULL" |
| 2 | `FormatService.createFormat(FormatDocument)` — `ownerUserId`를 안 넣는다 | **호출자 0개(사실상 죽은 코드)**. 그대로 두면 미래에 다시 NULL을 만들 수 있다 | `FormatService.java:68-88`. `grep -rn "formatService\.createFormat("` → 없음(컨트롤러의 동명 핸들러 `FormatController.java:71`은 `createFormatWithOwner`를 부른다 `:81`) |
| 3 | `FormatService.updateFormat/deleteFormat/listFormats` 구버전 | 호출자 0개 | 같은 grep |
| 4 | `ScheduleService.create/update/findAll` 구버전 | 호출자 0개. `ScheduleController`는 `findAllByOwner`·`createWithOwner`·`updateWithOwnerCheck`·`deleteWithOwnerCheck`만 쓴다 | `ScheduleController.java:47,64,83,100` |
| 5 | `createFormatWithOwner` / `importFormat` | **NULL 불가**. `principal.userId()`=`user.getId()`이고 `principal == null`이면 401 | `FormatService.java:481-502`, `:217-226`; `FormatController.java:74-81, 140-176`; `UserPrincipal.java:26-28` |

**추가로 발견한 것(중요, 원 지시에 없던 항목)**:

`ScheduleService.createWithOwner`의 포맷 소유권 검사가 **NULL 포맷을 아무에게나 허용**한다:

```java
// server/src/main/java/com/harupaper/server/schedule/ScheduleService.java:349-352
var formatOpt = formatRepository.findById(request.formatId());
if (formatOpt.isEmpty() || (formatOpt.get().getOwnerUserId() != null && !formatOpt.get().getOwnerUserId().equals(userId))) {
    throw new NotFoundException("Format not found: " + request.formatId());
}
```
`updateWithOwnerCheck`(`:429-432`)도 같다. 비교 대상인 `PrintNowController.java:71-74`는 `!userId.equals(...getOwnerUserId())`로 **NULL을 거부**한다.

결과적으로 **"사용자 X의 예약이 X 소유가 아닌 포맷을 가리키는" 상태가 만들어질 수 있다.** 그 상태에서 `DeviceSyncService.buildSnapshot`은 formatId로 렌더를 고르므로(`:210-228`) **X의 스냅샷에 X가 아닌 소유자의 렌더가 실린다** → strict를 켜면 그 렌더만 404 → 1.2의 조용한 실패. claim-legacy 이후에는 NULL 포맷이 사라져 새로 만들 수는 없지만, **그 전에 만들어진 예약은 남는다.**

→ **결론 1**: strict 전환의 사전 조건은 "NULL 0"만으로 부족하다. **"활성 예약 중 예약 소유자 ≠ 포맷 소유자인 것이 0"**도 확인해야 한다(런북 C 5단계에 SQL로 넣었다).
→ **결론 2**: 선택은 여전히 **(a)**다. 오히려 확인할 조건이 하나 더 늘었으므로 "켜 보고 아니면 즉시 끈다"가 가능한 플래그의 가치가 커졌다.

### 1.5 선택: **(a) 플래그 + 기한이 정해진 일몰(sunset)**

플래그의 유일한 실패 모드는 **"`false`인 채로 잊혀지는 것"**이다. 그러면 구멍이 그대로 남는다. 그래서 3단계를 계획에 못박는다.

| 단계 | 내용 | 조건 |
|---|---|---|
| **A-1** | 플래그 추가, 기본 `false`. 동작 불변. 지금 커밋 가능 | 없음 |
| **A-2** | `server/.env`에 `HARU_RENDER_OWNER_STRICT=true` → `docker compose up -d`(rebuild 없음) | 런북 C 완료 + 1.4의 교차 소유 예약 0 |
| **A-3** | 플래그를 **삭제**하고 거부를 무조건화. `.env`에서 그 줄도 지운다 | A-2 후 Pi가 **7일 연속** 정상 인쇄, `RENDER_OWNER_NULL` ERROR 0건 |
| **A-4** | V5 `NOT NULL` (1.8) | A-3 완료 |

7일인 이유: `RenderCleanupScheduler`가 `kind=scheduled` 렌더를 `targetDate < 오늘-7일`에 지운다(`RenderCleanupScheduler.java:112-142`). 7일이면 strict 아래에서 만들어진 렌더로 캐시가 한 바퀴 돈다.

### 1.8 V5 `NOT NULL`로 가는 길

**최종 지점이 맞다.** 다만 `renders`만으로는 반쪽이다 — 근본 원인은 `formats.owner_user_id`가 NULL일 수 있다는 것이므로 **두 테이블을 같이** 건다.

```sql
-- V5__owner_not_null.sql (A-3 이후)
ALTER TABLE `formats` MODIFY `owner_user_id` CHAR(36) NOT NULL;   -- fk_formats_owner는 유지된다
ALTER TABLE `renders` MODIFY `owner_user_id` CHAR(36) NOT NULL;   -- FK는 원래 없다(V2 주석: 이력 보존)
```

**걸 수 있는 시점**: A-3 완료(7일 무사고) + 두 테이블 NULL 카운트 0 재확인.

**깨질 수 있는 코드 경로**:

| 경로 | 무슨 일이 | 대응 |
|---|---|---|
| `RenderServiceImpl.savRender`(`:197-218`) | 포맷 소유자가 NULL이면 INSERT가 `SQLIntegrityConstraintViolation`. `RenderScheduler`는 잡고 넘어가고(`RenderScheduler.java:81-84`) `PrintNowController`는 500 | `formats`도 NOT NULL이면 애초에 발생 불가. 추가로 `savRender` 앞에 `Objects.requireNonNull(format.getOwnerUserId(), …)` 가드를 두면 원인이 명확한 예외가 난다 |
| `FormatService.createFormat`(죽은 코드) | INSERT 실패 | 1.6에서 삭제 |
| `AdminService.claimLegacyResources`(`:37-42`) → `FormatRepository/RenderRepository.updateOwnerForNull` | **안 깨진다.** `WHERE owner_user_id IS NULL`이 0행에 매치될 뿐 | 두 줄은 남겨두고 "이제 상시 0"이라는 주석만. `schedules/assets/commands/results`는 그대로 |
| `Render.ownerUserId` 엔티티 애노테이션(`Render.java:29-31`) | `ddl-auto: validate`는 **nullability를 검사하지 않는다** — 그대로 둬도 기동은 된다 | 문서 목적으로 `@Column(name = "owner_user_id", nullable = false)`로 갱신 |
| `DeviceSyncControllerOwnershipTest`의 "NULL 레거시 허용" 테스트(`:98-111`) | 의미가 사라진다 | strict 테스트로 교체(1.9) |
| `commands`·`results`의 `owner_user_id` | **범위 밖.** 여전히 NULL 허용이고 `V2` 주석대로 페어링 전 명령을 위해 필요하다(`DeviceSyncService.java:113-119`) | 건드리지 않는다 |

### 2.2 실제 동작에 영향이 있나 — **없다** (하지만 이유가 중요하다)

프로필 로드 흐름(`FormatEditPage.tsx:61, :71-84`): `useState(DEFAULT_PRINTER_WIDTH_PX)`로 시작해 마운트 직후 `deviceApi.get()` 결과로 덮는다. 실패하면 기본값 유지(`:78-81`).

그런데 그 값이 흘러가는 끝을 따라가 보면:

```
FormatEditPage(:324) → LayoutEditor(:15,:32,:146) → LayoutCanvas(:13,:41,:63,:89,:105,:110)
  → SlotCard(:131) → SlotContent(:19,:30) → renderImage(block, _printerWidthPx)
```

`SlotContent.tsx:72`의 시그니처가 `function renderImage(block: Block, _printerWidthPx: number)` — **언더스코어 접두사이고 본문에서 한 번도 읽지 않는다**(`:72-104`, 이미지는 `width: ${widthPercent}%`로만 그린다). 글자 크기는 `printerWidthPx`가 아니라 `SlotContent.tsx:10`의 `DEFAULT_DPI = 300`으로 환산한다(`:47, :115`).

→ **`printerWidthPx`는 현재 화면에 아무 영향이 없는 죽은 prop이다.** 1304든 1300이든 픽셀 하나 안 바뀐다. 그래서 이 과제는 **동작 수정이 아니라 경계 규칙·문서 정합성 수정**이고, 반대로 말하면 **회귀 위험이 거의 0**이다.

## 3. 런북 C — V4 적용 + claim-legacy (사용자가 직접 실행)

> **되돌리는 마이그레이션이 없다. 백업이 유일한 롤백 수단이다.**

> 전 구간 `~/Data/Haru-Paper/server`에서 실행한다. 다른 프로젝트 컨테이너는 건드리지 않는다.

### 0단계 — 사전 확인


### 1단계 — 백업 (필수, 먼저)

### 2단계 — 재빌드·재기동 (Flyway가 V4를 자동 적용)

### 3단계 — V4 결과 확인 (claim-legacy **전에**)

### 4단계 — `claim-legacy` 실행

엔드포인트: `POST /api/admin/claim-legacy` — **세션 로그인 + ADMIN 역할 + CSRF 헤더**가 필요하다
(`AdminController.java:135-148`, `SecurityConfig.java:83` `.requestMatchers("/api/admin/**").hasRole("ADMIN")`, `docs/server/auth.md:107`).
관리자는 `.env`의 `HARU_ADMIN_EMAIL`로 가입한 계정이다(`server/.env.example:5-7`, `docs/server/auth.md` 3절).

`docs/server/api.md` 7절의 curl 관례를 그대로 따른다:

```bash

# 관리자 로그인 (비밀번호는 셸 히스토리에 남지 않게 프롬프트로 받는다)

  -H 'Content-Type: application/json' \
```

- **기대 응답**(`AdminController.ClaimLegacyResponse`, `:215-231`):
  `{"updatedFormatCount":N,"updatedScheduleCount":N,"updatedAssetCount":N,"updatedRenderCount":N,"updatedCommandCount":N,"updatedResultCount":N}`

- **401이 나면**: 로그인 실패. 응답 본문의 ProblemDetail을 읽는다.

## 5. 범위 밖으로 남기는 것과 이유

1. **`SlotContent`의 죽은 `_printerWidthPx` 파라미터 제거, 실제 dpi 배선** — `SlotContent.tsx:10`의 `DEFAULT_DPI = 300`은 기기 프로필의 dpi가 300이 아니어도 300으로 환산한다. 현재 기기가 300dpi 한 대뿐이라 증상이 없다. M7 위젯 작업에서 편집기 미리보기를 손볼 때 같이 본다.
2. **`commands.owner_user_id` · `results.owner_user_id`의 NULL** — 페어링 전에 만든 명령을 버리지 않기 위해 의도적으로 NULL을 허용한다(`DeviceSyncService.java:113-119`, `V2` 주석). NOT NULL 대상이 아니다.
